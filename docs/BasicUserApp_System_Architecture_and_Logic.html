1. System Architecture Overview

BasicUserApp is engineered as a decoupled, client-server mobile solution. The mobile client (Flutter) provides an interactive user registration interface and dynamic user directory, communicating over RESTful HTTP endpoints with an Express.js backend.

2. Detailed Backend Logic (Node.js & Express)

2.1 Storage Auto-Initialization

When the server boots, initializeDataStorage() runs before the server accepts traffic. It recursively ensures that the backend/data/ directory exists and verifies the presence of users.json. If absent, an empty JSON array [] is initialized. This eliminates cold-start configuration errors.

2.2 Concurrency Queue & Atomic File Updates

Traditional file systems lack built-in row-level locking. To safely manage multiple incoming registration requests without corrupting data, two specific mechanisms are deployed:

1. In-Memory Promise Chain (Sequential Lock)
A promise-based mutex withFileLock(operation) queues all read-modify-write tasks sequentially. Even if multiple mobile clients submit registrations at the exact same millisecond, the operations are processed one after another in order.
2. Atomic Temporary File Renaming
Instead of writing directly to users.json, the backend writes to a unique temporary file: users.json.tmp.<timestamp>. Once writing is fully completed, fs.rename() atomically overwrites the main file. This ensures that a server crash or power interruption never leaves a corrupted, half-written JSON file.

2.3 Input Validation & Duplicate Checking

Every registration request hitting POST /api/users undergoes strict server-side validation:

  • Full Name: Checked for existence, non-whitespace content, and a minimum length of 2 characters.
  • Email Format: Validated against standard RFC-compliant regex /^[^\s@]+@[^\s@]+\.[^\s@]+$/.
  • Phone Number: Validated against pattern /^\+?[0-9\s\-()]{7,20}$/ ensuring at least 7 digits.
  • Duplicate Prevention: Case-insensitive comparison against existing records. If jane@example.com exists, attempting to register JANE@EXAMPLE.COM is rejected with an HTTP 400 error.

3. Detailed Frontend Logic (Flutter & Dart)

3.1 Networking & Addressing Strategy

Mobile OS networking differs significantly from standard desktop web development. The ApiConfig class abstracts this logic:

  • Android Emulator: Routes to http://10.0.2.2:5000 because the emulator runs inside a virtual router where 10.0.2.2 aliases the host PC's loopback interface.
  • Physical Android Devices: Connects to http://<PC_LAN_IP>:5000 over the local Wi-Fi router.
  • Why Localhost Fails on Mobile: In Android, localhost (127.0.0.1) resolves to the smartphone's internal loopback interface, completely missing the host computer's backend server.

3.2 UI State Machine in HomeScreen

The user interface implements a reactive state machine managed by Flutter's StatefulWidget lifecycle:

1
Client-Side Validation Phase
Form field controllers and GlobalKey<FormState> perform instant client-side checks for name length, email format, and phone structure.
2
Async Submission & Progress Locking
When submitted, _isRegistering is set to true. The button swaps its icon for an emerald CircularProgressIndicator and locks user inputs to prevent duplicate submissions.
3
User Directory Multi-State Handling
The Users List tab handles 4 distinct visual states: (A) Loading: shimmer/spinner; (B) Error: cloud-off illustration with detailed error text & retry button; (C) Empty: clean inbox icon with a 1-tap shortcut to registration; (D) Populated: scrollable card list with generated avatar initials, contact rows, and pull-to-refresh.

4. Android Native Layer & Toolchain Integration

4.1 Cleartext Traffic & Permissions

Modern Android releases (Android 9 / API 28 and above) block cleartext HTTP network traffic by default for security. In frontend/android/app/src/main/AndroidManifest.xml: 

<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<application
    android:label="BasicUserApp"
    android:usesCleartextTraffic="true">

Setting android:usesCleartextTraffic="true" permits the mobile app to communicate with local development servers over unencrypted HTTP without requiring SSL certificates during prototyping.

4.2 Build Alignment & NDK Configuration

In frontend/android/app/build.gradle.kts, the NDK was explicitly aligned with the system's installed NDK toolchain (ndkVersion = "30.0.16248370"). Release signing was mapped to signingConfigs.getByName("debug"), allowing immediate compilation into an installable release package:
